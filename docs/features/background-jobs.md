## Background jobs

`worker/jobs/queue.ts` (FLOW-27) is the outbox and work queue, stored in the `jobs` table.

- **Enqueue inside the change's transaction.** `enqueueJob(tx, { type, payload, idempotencyKey })` and `emitDomainEvent(tx, { name, entityId, data })` take the caller's transaction, so a rolled-back change never leaves a job behind. A repeated idempotency key is ignored. Domain events are jobs of type `event:<name>` (`<entity>.<past-tense verb>`, e.g. `client.created`).
- **Handlers** register by type in `createJobRegistry()` (`worker/jobs/cron.ts`). Handlers must be idempotent. An event with no subscriber succeeds as a no-op; any other job type without a handler fails. Each cron run completes the due events that have no registered handler in one statement *before* claiming its batch (`completeUnsubscribedEvents`, FLOW-184), so a 300-line stock count cannot queue real work behind 300 no-ops; events with a subscriber (for example notifications) still run in the batch.
- **Cron.** One Cron Trigger (`*/5 * * * *` in `wrangler.jsonc`) first emits `task.due` for tasks that came due (FLOW-58), then runs `runDueJobs`, which claims at most 10 due jobs (`FOR UPDATE SKIP LOCKED`) so each run stays within the 10 ms CPU budget. A throwing handler retries after 30 s, 1 min, 2 min, … (capped at 1 h) and is marked `failed` after 5 attempts. A job stuck in `running` for 10 minutes is reclaimed. Without a Hyperdrive binding the cron logs `jobs_skipped` and does nothing.
- **Retention** (FLOW-184, `worker/jobs/cleanup.ts`). After the batch, each cron run deletes up to 500 `succeeded` jobs that finished more than 30 days ago (pending, running and failed jobs stay; a job whose ingest receipt is still unprocessed stays too, because replaying that receipt needs it), and empties the raw `body` of up to 500 ingest receipts processed more than 90 days ago. The receipt row (source, record id, timestamps) stays, so posting the same record again still answers `duplicate: true`. The same step removes abandoned and long-archived files (see [Attachments](attachments.md#attachments)). What was removed appears in the `jobs_run` log line (`jobsPruned`, `receiptBodiesCleared`, `abandonedUploadsRemoved`, `archivedAttachmentsRemoved`); a failing cleanup logs `cleanup_failed` and is retried by the next run.
- **Admin API:** `GET /api/admin/jobs?status=failed` lists jobs; `POST /api/admin/jobs/<id>/retry` re-queues a failed job with fresh attempts.
