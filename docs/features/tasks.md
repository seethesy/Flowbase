## Tasks

One task model for every module (FLOW-58, `shared/tasks.ts`; service in `worker/records/tasks/tasks.ts`, API `worker/routes/tasks/tasks.ts`). A task has a title, description, type (`general | delegated | kitchen | production | truck_load | misc`), status (`todo | in_progress | blocked | done`), priority, due time, assignees, zero or more managers, its creator, links to an event, client, inventory item or BEO, a checklist, comments and attachments (`recordType: "task"`). Kitchen, production and truck-loading tasks are rows of the same `tasks` table, so they appear in the same lists.

- **Managers** (FLOW-323/324/344): `task_managers` stores each task's managers. Migration `0084` copies each former `overseer_id` into one manager membership before dropping the old column. New tasks copy the active Admin accounts at creation unless Settings → Defaults selects specific active Admin accounts; the creator is not added automatically. The API rejects non-Admin managers with 400. The creator or any manager may change managed fields. A deactivated manager stays in task history but receives no new notifications. The `overseer` API and field-registry key, `overseerId` list filter, and existing wording keys remain for saved layouts and views; the `overseer` response contains the manager list. New create/update requests use `managerIds`; `overseerId` input remains accepted for older callers.

- **Service API:** other modules call `createTask(tx, actor, input)` and `updateTask(tx, actor, id, patch)` inside their own transaction (`actor` is `null` for system changes); there are no task tables per module. Linked records must exist, and a person may link only records they can open.
- **Status rules:** moving to `done` records who completed it and when (`completedBy`, `completedAt`); saving `done` again keeps them; reopening clears them.
- **Who sees and changes what** (`shared/policy.ts`): FT+ see every task, everyone else the tasks they are assigned to, manage or created (`taskScope`). The communal list (`GET /api/tasks` without `mine=true`, FLOW-59) is open to every role: FT+ see every task, everyone else their own plus the open **unassigned** tasks (`visibleTasks`, FLOW-272), which they can pick up.
- **Audit and events:** every change writes an audit row (`task`; checklist changes are task updates, comments `task_comment`). A change of assignees emits `task.assigned` with `addedUserIds`, `removedUserIds` and `actorId`. Each cron run emits `task.due` once per open task and due time (`emitDueTaskEvents`; tasks more than 7 days overdue when first seen are skipped).
- **Pick up / Drop** (FLOW-344): anyone with `tasks.write` may join the assignees of an open task they can see through `POST …/claim`; the current assignees stay. `POST …/drop` removes only the caller. The row is locked for concurrent changes, `task.claimed` still tells managers on pick up, and `task.assigned` records additions and removals. Done tasks return 409 on pick up. Active staff without accounts can be assigned but receive no notifications. `GET …/assignments` reports each addition and removal with actor and time from the archived assignment rows. Moving a task to `done` emits `task.completed`. Each cron run also emits `task.due_soon` once per open, assigned task due within 24 hours (`emitDueSoonTaskEvents`).
- **Due buckets** (`dueBucket`, New York time): `overdue` = past its due time, `today` = later today, `upcoming` = after today or no due date. `GET /api/tasks?due=` filters by them.
- **Saved views** (`task_views`, FLOW-59 AC3): a person's own named filter sets; nobody else sees them.
- **Dashboard** (`GET /api/tasks/dashboard`, FLOW-61/344): `all`, `mine`, `managing` and `needsDelegation` sections return tasks with a `dueBucket` and retain completed tasks for `hideCompletedTasksAfterDays` (default seven). The earlier `overdue`, `today`, `upcoming` and `overseeing` sections remain for the existing screen. Needs delegation still requires `tasks.triage` and covers open unassigned tasks on events starting today through 14 days out, plus unassigned tasks on no event due by then or undated. Each section returns its count and 50 soonest-due tasks.
- **Notes and deletion** (FLOW-344): `notes` is a separate plain multi-line field from description and comments. Creator, managers and assignees may edit it; anyone who can open the task sees it. Changes are audited. The creator or a manager may archive any task; `POST …/restore` undoes it and retains its assignees.
- **Templates** (`task_templates`, `task_template_items`, FLOW-62): a name, an optional SOP link (http/https; copied into each task's description) and items with a title, type, `offsetDays` from the event's date (negative = before), an optional time (`HH:MM`, otherwise the event's start time) and a default position (stored on the task as `position`). `templateDueAt` does the date math in New York time; a time skipped by the spring clock change moves an hour later. `tasks.templates` edits them; anyone with `tasks.delegate` who can open the event applies one. Applying creates unassigned tasks and records each task's `templateItemId`; `(event_id, template_item_id)` is unique on `tasks`, so re-applying only adds items the event doesn't have, and a task someone archived isn't brought back. Removing an item from a template archives it.
- **Screens:** `/tasks` is the dashboard (with quick-assign under Needs delegation), `/tasks/all` the list with filters in the URL and saved views, `/tasks/templates` the templates, and the event hub's Tasks section lists the event's tasks and applies a template. `/tasks/<id>` shows one task: status, claim, reassignment and managers (for whoever manages it), checklist, comments and files.

| Route | Purpose |
| --- | --- |
| `GET /api/tasks?type=&status=&assigneeId=&overseerId=&eventId=&due=&unassigned=true&mine=true&includeDone=true` | Tasks the caller can see, newest first, paged; done tasks only with `status=done` or `includeDone=true`; 403 without `mine=true` for part-time staff |
| `GET /api/tasks/dashboard` | The caller's dashboard sections |
| `POST /api/tasks/<id>/claim` | Add the caller to the assignees (409 once done) |
| `POST /api/tasks/<id>/drop`, `GET /api/tasks/<id>/assignments` | Leave a task; read every assignee addition and removal with actor and time |
| `GET`/`POST /api/tasks/views`, `POST /api/tasks/views/<id>/archive` | The caller's saved views |
| `GET`/`POST /api/tasks/templates`, `GET`/`PUT /api/tasks/templates/<id>`, `POST …/archive` | Task templates (writes need `tasks.templates`) |
| `POST /api/tasks/templates/<id>/apply` `{eventId}` | Create the template's missing tasks on the event: `{created, skipped}` |
| `GET /api/tasks/<id>` | One task with checklist, comments and `canManage` |
| `POST /api/tasks`, `PATCH /api/tasks/<id>` | Create, or change any subset |
| `POST /api/tasks/<id>/archive`, `POST …/restore` | Archive or restore (needs `mayManageTask`) |
| `POST /api/tasks/<id>/checklist`, `PATCH`/`POST …/checklist/<itemId>[/archive]` | Add, tick, rename or remove a checklist item |
| `POST /api/tasks/<id>/comments` | Add a comment |
