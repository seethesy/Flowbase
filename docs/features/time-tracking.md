## Time tracking

Automatic activity time tracking (FLOW-119) measures in-app time per record and per type of work, without a timer. Schemas and constants live in `shared/time-tracking.ts`, the browser logic in `src/services/time-tracking.ts` (`ActivityTracker`) and `src/app/useActivityTracking.ts`, and the API in `worker/routes/time-tracking.ts` with logic in `worker/records/time-tracking.ts`.

| Route | Purpose |
| --- | --- |
| `POST /api/time/sessions` | `{sessions: [{id, startedAt, endedAt, recordType, recordId, activity}]}`, up to 100. Always the caller's own time |
| `GET /api/time/report?from=&to=&userId=` | Effort per event (counting its proposals, tasks and BEO) with its booked total (the payment schedule's total, FLOW-221; null when no schedule is recorded or the viewer may not see the event's money, per `canSeePayments`), effort per proposal, and workload per user and activity type, for New York dates (the last 30 days by default) |

- **What counts:** time accrues only while a Flowbase tab is visible and the user has typed or clicked within the idle cutoff (5 minutes by default; Admin changes it in business settings, FLOW-45, and open tabs pick it up when they next load settings). An idle session ends when the cutoff passes; hiding the tab ends it at once, and time starts again with the next input. Only time inside Flowbase is measured.
- **What it's credited to:** the screen decides (`contextForPath`): leads, clients and events credit the record on screen; a proposal open on its event hub (`?proposal=<id>` in the address) credits that proposal as proposal work, and a task page credits the task as prep for Sales Managers and assigning for everyone else (FLOW-167, Ash 2026-10-29); the demo Proposals pipeline, venues and inventory credit only the activity type (proposal work, event planning, inventory, kitchen for the ingredient catalog); everything else is "general". A BEO is credited as BEO editing while its own page is open, `/events/<event id>/beo/<beo id>` (FLOW-221; the hub's BEO section links to it with "Open BEO page"); the Worker accepts a BEO id only for a BEO of an event the user can open, and BEO time counts toward its event's effort row.
- **Requests:** the browser sends at most one request a minute (`FLUSH_INTERVAL_MS`). An open session is resent with a later end under the same id and stays one row (`activity_sessions`, unique on user and session id); its end only ever grows. A request carries at most 100 sessions (`MAX_BATCH_SESSIONS`), the open one included; up to 100 finished sessions wait in the browser and go oldest first in later requests. Only the session versions a request carried leave the queue: a failed or rate-limited request keeps them for the next try, a request the API rejects drops only what it carried (FLOW-202). A 401 or 403 stops tracking for that page, so until sign-in (FLOW-36) nothing is recorded. Closing the tab can lose up to a minute that wasn't sent yet.
- **Who sees what** (`timeReportScope` in `worker/policy.ts`): Admin and Sales Manager see everyone's time and can narrow to one user; everyone else sees only their own. Events and proposals in the effort report also follow event visibility, and proposal rows need proposal access. Until the users table exists (FLOW-37) users show as ids.
- **Notice:** a "Time tracking is on" notice shows on first use (remembered per browser until sign-in exists) and on the Settings page.
