## Core records

Clients (FLOW-53), venues (FLOW-54) and events (FLOW-55) live in Postgres and are served by `worker/routes/records.ts`; Zod schemas in `shared/core-records.ts` are shared by the API and the screens in `src/features/{clients,venues,events}.tsx`.

- **Data cache** (FLOW-189, ADR-01): screens load API data through TanStack Query with a key per resource (`useResource` in `src/app/useResource.ts`, `usePagedList` in `src/app/paging.tsx`), so forms on one page share one request for the same list. A save marks everything stale; the screen on view reloads what it shows.
- **Paging** (FLOW-179, `worker/records/paging.ts`): every list endpoint (records, history, status history, leads and duplicates, inventory items, movements, cost history and counts) returns one page in its own order: 100 rows by default, `?limit=` up to 500. The body is still the array of rows; `X-Has-More: true|false` says whether more exist and `X-Next-Cursor` is passed back as `?cursor=` for the next page. Cursors are keyset positions (the last row's sort values, ending with its id), so paging returns every row once even while rows are added; a cursor the server can't read answers `400`. Screens search and filter on the server and show **Load more** (`src/app/paging.tsx`); pickers that must be complete load every page (`allPages` in `src/services/core.ts`), and the event form and lead conversion search clients as you type. The Events screen opens on the past 7 days through the next 30, soonest first, and its From/To dates reach any other range. List joins use maps (FLOW-180), and `tests/db/list-cpu.test.ts` keeps the median CPU of one list call under 30 ms with 2,000 items and 600 events.
- **Who sees what** (`shared/policy.ts`, FLOW-38): Admin, Technical and Sales Manager see every client and event; a salesperson sees the clients and events assigned to them (their new clients are assigned to them); other staff see the events they lead or assist or have a shift on (FLOW-140) and no clients. Records a user can't see answer 404. Venues are visible to everyone. Writes are open to Admin, Technical, Sales Manager and salespeople.
- **Stale saves** (FLOW-186): `PUT` on a client, venue, event or inventory item carries the `updatedAt` the form loaded (`withVersion` in `shared/schema-primitives.ts`; a body without it answers 400). The save locks the row and applies only if it still has that version; otherwise it answers `409 STALE` and changes nothing, contacts and areas included. The edit forms (`StaleReload`, `src/components/stale-reload.tsx`) then say the record changed, load the current version and let the user make their changes again. Archive, restore and status changes keep their own rules.
- **Authorization under concurrent changes** (FLOW-199): client and event update, archive and restore, and lead status changes and conversion lock the record and then check visibility on the current row inside their transaction (`findVisibleClient(…, "update")`, `lockVisibleEvent`, `lockVisibleLead`). A reassignment that commits first makes the previous owner's change answer 404 and write nothing (no child rows, audit entries or jobs); one that comes second waits. A save uses the current salesperson, so a stale copy can't restore the previous one. Bulk lead assignment locks its leads, so a lead converted first is refused as no longer open. Clients an event or a conversion refers to are locked for share until it commits.
- **Contact details** (F-01-04): client contact email/phone and venue contacts come back as `null` for anyone who isn't FT+. An update that omits a contact's email or phone keeps the stored value.
- **Duplicates:** creating a client whose contact email or phone matches an existing contact answers `409 POSSIBLE_DUPLICATE` with the matches, and the form offers "Create anyway" (`allowDuplicate: true`). A salesperson is only warned about their own clients; a match they can't see is saved as `possibleDuplicateOf`, which only Admin, Technical and Sales Manager see (`?flagged=true`), and emits `client.duplicate_flagged`.
- **Person clients** (FLOW-352, `clientNameFor` in `shared/core-records.ts`): a client of kind `person` and its Primary POC are one person, so its name is always its first named `primary_poc` contact's name. The server enforces it on every create and update (`insertClient`, `updateClient`; a different name sent for a Person client is replaced), on lead Closing (the name entered is the POC's too; linking a contactless Person client to a lead names it for the lead added as its POC) and on event import. The client form hides the Name input for a Person and needs a Primary POC; the Clients table's Client column isn't editable for a Person (rename the Primary contact instead). Switching Organization → Person takes the POC's name; Person → Organization keeps it, now editable. A Person with no Primary POC keeps the name it was given. Migration `0089_flow_352_person_client_names` renamed existing Person clients to their POC's name, with one system audit row each (A1).
- **Events:** only title, date, start time and client are required. Times are entered as New York wall-clock times and stored as UTC (`shared/time.ts`); an end time before the start runs past midnight. Picking a venue copies its address (when the address is empty) and its areas; per-event areas can be added. The venue arrival time (`arrivalTime`, FLOW-140) is a time on the event date. `booked_at` records the first time the event reaches Negotiation (or a later status other than Lost, if it skipped Negotiation). The salesperson is a user id; Production Leads are named only through their own route (see Staff roster below), so the event form never changes them.
- Every create, update, archive and restore emits a domain event (`client.created`, `event.updated`, `venue.archived`, …) in the same transaction. Archive and restore for every record go through `setArchived` (`worker/records/archive.ts`), which sets `archived_at`, writes the audit row for audited records and emits `<record>.archived` / `.restored` in one transaction; inventory sections have no event. Route files run record functions with `recordRunner` (`worker/hono.ts`), which passes the database and the signed-in actor.
- **Lifecycle** (FLOW-56, `shared/event-lifecycle.ts`): Inquiry → Pitching → P creation → Initial P sent → Negotiation → Closing → Closed (paid and signed) → Preparation → Finished | Lost. An event can be created in any status. After that the status never changes through `PUT`: Admin or the event's salesperson changes it with `POST /api/events/<id>/status` (`{ status, reason? }`) to any other status, and the system moves it with `advanceEventStatus` (in `worker/records/events.ts`, for the features that drive it), which allows only the next status or Lost and refuses anything else with `409 INVALID_TRANSITION`. Finished and Lost are final for the system. Every change writes a row to `event_status_history` (who, when, from, to, why, manual or automatic; `GET /api/events/<id>/status-history`), writes the audit row and emits exactly one domain event, `event.<new status>` with `{ from, to, reason, manual }`.
- **History** (FLOW-41, `worker/audit/log.ts`): every create, update, archive and restore of a client, venue or event (FLOW-161) writes one row to the append-only `audit_log` in the same transaction: actor, time, and a before/after diff of only the changed fields, keyed by their API names (a client's contacts, a venue's areas and contacts, and an event's area names are fields of their record). An update that changes nothing writes no row. `GET /api/{clients,venues,events}/<id>/history` returns it newest first to anyone who can see the record, hiding what the record itself hides from them (contact details from part-time users, the possible-duplicate match from salespeople); a change made only to hidden fields doesn't appear. Inventory items, inventory sections and lead changes are audited the same way (FLOW-185, below), and so is every stock movement (FLOW-168). No route updates or deletes audit rows.
- **Event hub** (FLOW-57): `/events/<id>` is one page per event, loaded from `GET /api/events/<id>/hub`, which returns the event, its client (or `null`), the sections to show whether the user may edit, and whether they may change the status (FLOW-56). The full set of sections is defined in `shared/event-hub.ts`. Only the sections whose module exists are listed (`builtSections` in `worker/records/events.ts`: details, client, proposal, inventory, tasks, staff, files and history), and each module ticket adds its own. The tasks section is FLOW-59's (see Tasks). **History** (FLOW-166) lists the event's audit rows (FLOW-161) from `GET /api/events/<id>/history`, newest first, for anyone who can open the event. Changes to people and contacts, stored by id, show as "changed" without the id. The calendar (FLOW-63) opens the hub when an event is clicked. "← All events" and archiving go to Events › Overview, and `/events` redirects there (FLOW-349). Outside Edit mode the client's name in Event details and in the Client card links to the client's page (FLOW-350). **Status** (FLOW-350): the pill under the title is a dropdown of every status for whoever may change it (`canChangeStatus`), saved with `POST /api/events/<id>/status` without a reason; others see the plain pill. The status history is at the top of the History card. **Folding** (FLOW-350): every card has the fold arrow (FLOW-347); Event details, Notes, Client and Proposals start open, the others folded (`FoldableSections` around each hub section). The client section needs access to the client record, so staff who only work the event see the client's name in the details but not the client, and contact details follow F-01-04. Edit and Archive appear only for roles with `events.write`. **Edit mode** (FLOW-335): Edit turns the event's own fields into inputs in place (the title in the heading; date and times, client and point of contact, venue, address, areas, event type, service type, food service style, guests, servings, dress code and arrival time in Event details; transportation and internal notes in Notes), saved together through `PUT /api/events/<id>` with the loaded `updatedAt` (a stale save reloads the current version and says so). Status changes in the dropdown under the title, not in Edit mode; Planning outputs and the other sections keep their own editors. Cancel drops the changes; leaving with unsaved changes asks first. The `EventForm` drawer stays for creating events.
- **Proposals** (FLOW-122/123, `shared/proposals.ts`, `worker/records/proposals.ts`, `src/features/event-proposals.tsx`): the hub's Proposals section, for anyone with `proposals.read` (Admin, Technical, Sales Manager, salespeople) on an event they can open. An event has one or more proposals (`proposals`), each with a title, notes, an assigned salesperson (the event's by default; Admin, Technical and the Sales Manager may pick another) and its own stage, separate from the event's status: Client communication → Menu curation → Revisions → Finalized → Approved → Sent → Signed | Lost. People with `proposals.write` move only the manual stages (Client communication, Menu curation, Revisions, in any order, and back to Revisions from Finalized, Approved or Sent) and Lost, which needs a reason and is final like Signed; `POST /api/proposals/<id>/stage` refuses Finalized, Approved, Sent and Signed (AC1), which only their actions set. Losing a proposal when the event has no other proposal that isn't lost also moves the event to Lost automatically (unless it is already Finished or Lost), with the reason in its status history. Every stage change writes `proposal_stage_history` (who, when, from, to, why, and whether a person or an action made it), an audit row (`proposal`) and `proposal.stage_changed` for the sales tracker (FLOW-117). **Versions** (FLOW-123, ADR-16): the finalized proposal is uploaded as the Google Docs Word export (.docx), optionally with a PDF of the same version; anything without a .docx is refused before upload and by the API with the export hint. Files go straight to R2 with signed URLs (`POST /api/proposals/<id>/versions`, then `…/versions/<versionId>/complete`, which checks each file arrived). Completing gives the version the next number, makes it current, emits `proposal.version_uploaded` and moves the proposal to Finalized (from a manual stage or Approved; a sent proposal goes back to Revisions first, a signed or lost one takes no uploads). Versions are never edited or deleted: no route changes one, and older versions stay downloadable. Mapping the .docx (FLOW-124/125) and approval, sending and booking (F-11-06, F-12-01) come later. The `/proposals` screen now shows the real sales tracker, and the current version review records a confirmed total in cents.

- **Proposals library** (FLOW-276, `listProposalFiles` in `worker/records/proposals.ts`, `src/features/proposal-library.tsx`): `/proposals` shows one file per event the user can open, the latest uploaded version among its proposals, with no label by default, Approved when that version's latest approval is approved (as on the event page) and Final when the client signed a contract for that version, the .docx and optional PDF links, upload date and a link carrying only the event's name. List or grid view, remembered per user in the browser; search by name and filter by upload date. Read only: a proposal is renamed on its event page.
- **Sales tracking** (FLOW-117/118/121, `shared/sales.ts`, `worker/records/sales.ts`, `src/features/sales.tsx`): `/sales` (moved from `/proposals` by FLOW-276) lists scoped leads, clients, events and proposals with filtering, sorting, personal saved views and CSV export. Proposal stages reflect current database state and realtime refreshes. Each client's Proposal tracker tab shows every current event status, proposal version totals, received payments, balance and lifetime booked total. `/sales/reports` shows pipeline, booked totals by event month and decided-proposal win rates by salesperson and lead source. Totals are blank until the current proposal version has a reviewed total. Communication activity and next follow-ups await FLOW-120.
- **Staff roster and Production Leads** (FLOW-140, `shared/event-staff.ts`, `worker/records/event-staff.ts`, `src/features/event-staff.tsx`): the hub's Staff section, laid out like the BEO's Staff Roster. An event has shifts (`event_shifts`): pull/load day, setup day and event day, each with its own New York date, start and end time (an end before the start runs past midnight) and activities; the pull/load and setup days default to the day before. Each shift has staffing slots (`event_staff_slots`) with a position from the `staff_position` list (Settings, so roles are configurable), a department and an assignee or none. Repeated positions on a shift are numbered ("Server #5"), open slots read "– open", and the staffing breakdown counts slots and filled slots by department (Management, Kitchen, Service, Bar, Decor/Setup, Pull/Load, Transport, Other; a new slot's department defaults from its position and can be changed). Anyone who can open the event reads the roster; `events.write` changes it. Assigning someone whose other shift overlaps (on any event that isn't archived or Lost) still saves, and both slots show a double-booking warning naming the other event, or "another event" when the viewer can't open it; back-to-back shifts don't count. Each assignment emits `event.staff_assigned` (and a removal `event.staff_unassigned`) with the slot, user and previous user, which the notifications (FLOW-43) follow; shift and slot changes are audited as `event_shift` and `event_staff_slot`. Production Leads: `events.production_leads` (Admin and Sales Manager) names one primary and up to 10 assistants; assistants need a primary, the primary must be an active full-time user, assistants active staff, and the change emits `event.production_leads_changed` for production alerts (FLOW-153). Staffing slots from the mapped proposal (F-11-04) wait for FLOW-125.
- **Event timeline and production schedule** (FLOW-126, `shared/event-timeline.ts`, `worker/records/event-timeline.ts`, `src/features/event-timeline.tsx`): the hub's Timeline section. An entry (`event_timeline_entries`) is a kind (`production` for pre-event milestones, `event` for the day of), a New York date with start and end time (an end before the start runs past midnight), an activity, who and where. Who is a staff member, a role from the `staff_position` list, or an outside event partner from the vendor directory (`vendors.type = event_partner`), who needs no Flowbase account; where is one of the event's areas. Days show in date order with entries in start order; the event's own day always shows, and the staff shifts (FLOW-140) on each day are listed read-only above its entries. Lines of the mapped proposal's timeline (FLOW-125) are offered as suggestions, pre-filled where the line starts with a time ("4:00 pm - 5:30 pm Guest arrival"), and stop being suggested once added. Anyone who can open the event reads it; `events.write` changes it; changes are audited as `event_timeline_entry`. Not built: freezing edits after BEO approval (F-15-02) and carrying the timeline onto the BEO (FLOW-143).
- **Start planning, pull list and kitchen menu** (FLOW-133/134/137, `shared/planning.ts`, `shared/pull-list.ts`, `shared/kitchen-menu.ts`, `worker/records/planning.ts`, `pull-list.ts`, `kitchen-menu.ts`, `src/features/event-preparation.tsx`): "Start planning" (Admin, Sales Manager or the event's salesperson, on a Closed event) moves the event to Preparation, writes one `event_planning_steps` row per step and queues one `planning.step` job for each step that has a module: confirm holds, generate the pull list, generate the kitchen menu. Steps whose modules aren't built (requirements, production tasks, BEO draft, calendar) are recorded as skipped so the hub shows the whole workflow. The pull list (`pull_lists`, `pull_list_lines`) is built from the mapped proposal's non-menu lines: kits and services expand through `itemRequirements`, lines with no quantity are TBD and flagged, untracked lines become name-only lines; groups are Kitchen equipment, Decor and Supplies. Anyone on the event moves a line through To pull, Pulled, Loaded and Returned (who and when are stamped); `events.write` edits lines, sets the pull date and time (New York time) and puller, and regenerates. The kitchen menu (`kitchen_menus`, `kitchen_menu_lines`) is built from the proposal's menu lines matched to dishes; the Kitchen Lead or `events.write` plans quantities and when food leaves the kitchen, and kitchen tasks are ordinary tasks of type `kitchen` linked to the event. Regenerating shows a preview first: lines match on a source key, hand edits and hand removals are kept unless the user chooses to discard them, and lines the proposal dropped are archived. Changes are audited as `pull_list`, `pull_list_line`, `kitchen_menu`, `kitchen_menu_line` and `event_planning`. Not built: requirements, production tasks and the BEO draft steps, and the print layout for the kitchen menu beyond the browser's print.
- **Banquet event order** (FLOW-143/144/148, `shared/beo.ts`, `worker/records/beo.ts`, `worker/routes/beo.ts`, `worker/beo-sync.ts`, `src/features/event-beo.tsx`): the BEO is assembled live from the event, client and venue, kitchen menu, staff roster, timeline and pull list, in ten sections: header; event, client, point of contact and venue; summary; food setup with allergens and dietary tags; staff roster; timeline; kitchen and decor equipment; venue layout; setup details and cleanup checklist; additional notes. No section has a price, cost or payment field. Open staff slots show as OPEN and unplanned quantities as TBD. The `beos` row keeps only the status (`working_on`, `pending_approval`, `approved`), the approval, the free-text parts no other record owns yet (setup details, cleanup checklist, additional notes) and `snapshot`, the field values at the last check. A new BEO starts as `working_on`. Approval goes through the approvals engine as subject `beo` (approver: Sales Manager; Admin too): anyone with `events.write` requests it, or the Sales Manager or Admin approves directly. Approving emits `beo.approved`. An approved BEO stays editable. After every successful write under `/api/events/<id>` (`beoSync` middleware), and when its own text is saved, `syncBeo` compares the BEO's fields with the snapshot. Once the BEO has been approved, each changed field is written to `beo_changes` (field, old value, new value, who, when) and stays marked "changed since approval" until the next approval; if the BEO was approved, `beo.changed_after_approval` is emitted, which tells the staff assigned to the roster (type `beo_changed`: in app and email, plus SMS through the stub outbox when the event is within 48 hours, to people who opted in; `beo_changed` is in the default urgent types) and the active Admins (FLOW-227): consent, the monthly cap with email fallback and one row per recipient and change follow FLOW-52's `routeSms`; the change's own person is left out). A change to a key field (business setting `beoKeyFields`, default `date_time`, `location`, `guest_count`, `menu`) returns an approved BEO to `working_on`. Field keys: see `beoFields` in `shared/beo.ts`; contact phones and emails are never part of a tracked field. Access: anyone who can open the event reads the BEO (unassigned staff get 404); `projectBeo` in `shared/policy.ts` is the one projection every surface must use, and leaves client and venue phones and emails to full-time staff and up. Printing and offline reading are described below (FLOW-149, FLOW-150). Not built: the `beo_draft` planning step runner (it stays skipped).
- **BEO schedule, setup, cleanup and layouts** (FLOW-145/146/147/65, `worker/records/beo-parts.ts`, `beo-edit.ts`, `src/features/beo-schedule.tsx`, `beo-areas.tsx`, `beo-layout-editor.tsx`, `calendar-detail.tsx`): the Timeline section shows each day's staff shifts (setup team, hours, activities) above a Start/End/Activity/Who/Where table. The run of show (`beo_run_of_show`, `beos.run_of_show_mode` auto/on/off) is minute-by-minute rows; in auto mode it shows once the guest count reaches the business setting `runOfShowGuestThreshold` (default 150). Setup and layout areas (`beo_areas`, `kind` setup or layout) are seeded from the event's area names; setup areas take reference and actual photos, layout areas take an image (attachment record type `beo_area`, groups `reference`, `actual`, `image`, `annotated`). Layout annotation uses Excalidraw (MIT), lazy-loaded so it stays out of the app shell (its chunks are exempt from the 500 kB gate in `scripts/check-bundle-size.mjs` only while they are off the first-load path): the scene (elements only) is stored on the area and a rendered PNG is uploaded as the `annotated` attachment, which the BEO and print show. Copying a layout adds the venue's named areas or a past event's layout areas at the same venue (names, notes and scene, FLOW-237: and the plan image and annotated PNG, each copied to a new R2 key through the `FILES` binding's `get`/`put`, so archiving the source never removes the copy; without that binding, as outside production, no images are copied). The cleanup checklist (`beo_checklist_items`) is seeded from the business setting `cleanupTemplate` (never changed by edits) and anyone who can open the event checks items off, stamping who and when. Calendar detail mode (FLOW-65): with "Detail mode" on, clicking an event shows its BEO details, read only, from the same role projection (`projectBeo`), so part-time staff see no contact details. The old `beos.cleanup_checklist` column is unused.
- **Payment schedule, payment log, reminders and overdue** (FLOW-131/132, `shared/payments.ts`, `worker/records/payments.ts`, `src/features/event-payments.tsx`): the hub's Payments section. The schedule (`payment_schedule_items`) is deposit, installment and balance items with an amount and a New York due date, optionally added from a mapped proposal's payment schedule. Payments (`payments`) record method (card via Square, Zelle, ACH, wire, check, cash), amount, date received, a reference and who recorded it. Money is integer cents; the reference is refused if it holds a run of 13 to 19 digits (a card number), so only a last 4 or a confirmation code is kept. Received money is applied to the schedule earliest due date first; the balance is the schedule total less what was received, and an item is overdue when it is past its due date with money still owed. Only full-time staff who may see the event's financials (Admin, Technical, Sales Manager and the event's own salesperson) read payments; everyone else gets a 403 and no Payments section. `payments.record` writes. Recording a payment emits `payment.recorded`. The cron (`emitPaymentReminders`) queues `payment.due` for the event's salesperson once per item and due date when it falls within the **Payment reminder days** setting (default 3), and `payment.overdue` once per item and due date after it passes; both are internal and use the generic notification payload. Not built: the overdue flag on the sales tracker and Sales Manager dashboard.
